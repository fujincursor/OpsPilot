# M6 - 新需求设计流程 · 详细设计

本文档对 **M6 新需求设计流程** 模块进行详细设计，包括业务边界、数据模型、接口定义、状态与流程、与上下游的集成方式及工作台页面映射。依据 [产品设计文档-运维Agent生产系统.md](产品设计文档-运维Agent生产系统.md)、[模块设计文档-运维Agent生产系统.md](模块设计文档-运维Agent生产系统.md)、[产品架构文档-运维Agent生产系统.md](产品架构文档-运维Agent生产系统.md)。

---

## 1. 模块概述

### 1.1 职责边界

- **技术方案与设计说明生成**：基于工单（Ticket）与 M4 分析结果，结合 M3 知识库检索与代码库只读上下文，由 Agent 生成技术方案或设计说明，包含模块划分、接口定义、数据流、涉及文件建议等；**不直接生成代码**；代码由 M8 在 M7 Review 通过后生成。
- **设计文档产出**：输出结构化设计文档（DesignDoc），包含概述、模块划分、接口说明、建议涉及文件等，供 M7 展示与 Review、M8 消费。
- **与工作流衔接**：由工作流在「需求分类完成且类型为新需求（feature）」后触发；设计就绪后进入 M7 人工 Review；Review 通过后由工作流触发 M8 代码生成。

### 1.2 不归属 M6 的内容

- **需求分类与工单创建**（归属 M4）。
- **方案/设计/代码的展示与通过/驳回**（归属 M7 人工 Review 工作台）。
- **代码生成与语法校验**（归属 M8）。
- **测试用例与执行**（归属 M9）。
- **项目与 Agent 配置**（归属 M1）；M6 仅消费 M1 的 Agent 配置与项目隔离信息。

## 2. 数据模型

### 2.1 ER 关系概览

```mermaid
erDiagram
    Ticket ||--o| DesignDoc : "1:1"
    Ticket {
        string id PK
        string projectId FK
        string title
        string description
        string type
        string status
        datetime createdAt
    }
    DesignDoc {
        string id PK
        string ticketId FK
        string overview
        json modules
        json interfaces
        json suggestedFiles
        string status
        datetime createdAt
        datetime updatedAt
    }
```

- **Ticket** 由 M4 创建并写入分析结果（AnalysisResult）；M6 仅消费与扩展，不拥有 Ticket 实体。
- **DesignDoc** 为 M6 核心产出，与 Ticket 一对一；供 M7 展示、M8 消费。

### 2.2 实体定义

#### 2.2.1 DesignDoc（设计文档）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | string | 是 | 主键 |
| ticketId | string | 是 | 关联工单，唯一 |
| projectId | string | 是 | 项目 ID，冗余便于按项目查询 |
| overview | string | 是 | 设计概述（自然语言，整体方案说明） |
| modules | json | 否 | 模块划分列表，如 [{"name":"模块名", "description":"说明", "responsibilities":["职责1","职责2"]}] |
| interfaces | json | 否 | 接口定义列表，如 [{"name":"接口名", "method":"GET/POST", "path":"/api/...", "description":"说明"}] 或数据流/API 描述 |
| dataFlow | string | 否 | 数据流或流程说明（自然语言或结构化摘要） |
| suggestedFiles | json | 否 | 建议涉及文件列表，如 ["src/xxx/yyy.js", "test/xxx.test.js"] |
| status | string | 是 | generating / ready / failed |
| errorMessage | string | 否 | status=failed 时记录失败原因 |
| createdAt | datetime | 是 | 创建时间 |
| updatedAt | datetime | 是 | 更新时间 |
| createdBy | string | 否 | 触发方式：workflow / manual，可选 |

**约束**：一个 Ticket（且 type=feature）至多一条 DesignDoc；同一 ticketId 重复触发生成时可覆盖或版本化（由实现决定）。

#### 2.2.2 对 Ticket / AnalysisResult 的依赖（M4 产出）

M6 读取的工单与分析信息包括：

- **Ticket**：id, projectId, title, description, type, status, createdAt 等。
- **AnalysisResult**：ticketId, type（bug/feature）, scopeSummary, affectedModules[], confidence。

M6 不修改 Ticket 的 type；仅在工作流驱动下为 type=feature 的工单生成/更新 DesignDoc，并可能更新工单状态（如 design_ready）由工作流或 BFF 约定。

## 3. 接口设计

### 3.1 设计文档（DesignDoc）

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| POST | /api/projects/:projectId/tickets/:ticketId/design/generate | 触发生成设计文档（同步入参，异步执行时返回 taskId） | 项目成员（demander/reviewer/admin） |
| GET | /api/projects/:projectId/tickets/:ticketId/design | 获取当前工单的设计文档 | 项目成员 |
| GET | /api/projects/:projectId/features | 分页列表：仅 type=feature 的工单，支持状态筛选 | 项目成员 |

**请求/响应示例（触发生成）**：

- 请求：`POST /api/projects/:projectId/tickets/:ticketId/design/generate`  
  Body: `{}` 或空
- 响应（异步）：`202 Accepted` Body: `{ "taskId": "...", "message": "设计文档生成已提交" }`
- 响应（同步超时前完成）：`200` Body: `{ "id": "...", "ticketId": "...", "overview": "...", "modules": [...], "interfaces": [...], "status": "ready" }`

**请求/响应示例（获取设计文档）**：

- 请求：`GET /api/projects/:projectId/tickets/:ticketId/design`
- 响应：`200` Body: `{ "id": "...", "ticketId": "...", "overview": "...", "modules": [...], "interfaces": [...], "dataFlow": "...", "suggestedFiles": [...], "status": "ready", "createdAt": "...", "updatedAt": "..." }`
- 若未生成或生成中：`200` Body: `{ "status": "generating" }` 或 `404`（由实现约定）

### 3.2 与工作流联动（内部）

| 用途 | 说明 |
|------|------|
| 工作流触发 | 工作流在「M4 分析完成且 type=feature」后调用 M6 的 GenerateDesign(ticketId)；可异步入队，Worker 消费后调用 Agent 并写回 DesignDoc |
| 状态回写 | M6 将 DesignDoc.status 更新为 ready 或 failed 后，由工作流轮询或事件驱动进入 M7「待 Review」节点 |

## 4. 状态与流程

### 4.1 DesignDoc 状态

```mermaid
stateDiagram-v2
    [*] --> generating : 触发生成
    generating --> ready : 生成成功
    generating --> failed : 生成失败
    ready --> [*]
    failed --> generating : 重新生成
```

- **generating**：Agent 正在执行需求理解与设计生成；前端可展示 Loading 或进度提示。
- **ready**：设计文档已落库，可供 M7 展示与 Review；M8 在 Review 通过后消费。
- **failed**：生成失败（如 LLM 超时、检索异常）；可展示 errorMessage，支持「重新生成」。

### 4.2 新需求设计主流程（M6 段）

1. 用户提交需求 → M4 分析 → 分类为新需求（feature），创建/更新 Ticket 与 AnalysisResult。
2. 工作流根据 type=feature 触发 M6：调用 GenerateDesign(ticketId)（同步或异步）。
3. M6 拉取工单与 M4 分析结果，调用 M3.Search(projectId, query) 与代码库只读上下文，由 Agent 生成 overview、modules、interfaces、dataFlow、suggestedFiles，写入 DesignDoc，status=ready。
4. 若失败则 status=failed，写 errorMessage；工作流可重试或进入「需人工处理」分支。
5. 设计就绪后，工作流创建 M7 的「设计 Review」任务；用户在工作台查看 DesignDoc 并完成 Review。
6. Review 通过后，工作流触发 M8 代码生成（输入 DesignDoc）；M6 不再参与后续环节。

---

## 5. 业务规则

- **入口校验**：仅当 Ticket.type=feature 时允许生成 DesignDoc；非新需求工单调用生成接口应返回 400 或明确错误提示。
- **项目与权限**：所有接口按 projectId 隔离；调用方须具备该项目成员身份（由 M1 或 BFF 校验）。
- **知识库就绪**：建议在 M4 需求提交入口已做知识库就绪校验（M2）；M6 执行时若发现项目知识库未就绪，可记录失败原因并置 status=failed。
- **幂等与重试**：同一 ticketId 重复触发生成时，可由实现决定覆盖原 DesignDoc 或生成新版本；重试时清空原 failed 状态再置为 generating。
- **输出约束**：DesignDoc 仅输出结构化设计说明与建议文件列表，不包含可执行代码；代码由 M8 生成。

---

## 6. 与上下游集成

- **M4**：消费 Ticket 与 AnalysisResult；不修改 M4 数据。工单由 M4 创建，M6 仅读写 DesignDoc 及可选工单状态字段（若约定由 M6 更新 design_ready）。
- **M3**：调用 Search(projectId, query) 获取知识库与代码索引检索结果，作为 Agent 上下文。
- **M1**：获取 GetAgentConfig(projectId)、GetProject(projectId)，用于加载 Prompt 与模型配置；不写 M1。
- **M7**：M7 通过 GetDesignDoc 或 BFF 聚合获取 DesignDoc 内容，展示在 Review 工作台；M6 不直接调用 M7。
- **M8**：M8 在 Review 通过后由工作流触发生成代码，输入为 DesignDoc；M6 不直接调用 M8。
- **工作流**：M6 由工作流在「分析完成且 type=feature」节点触发；DesignDoc 就绪或失败后，由工作流推进到 M7 或重试/人工处理节点。
